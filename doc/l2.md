# L2

The RTL827x provides access and configuration options to an L2 table that
is used to associate device-MACs with ports on which those devices can
be reached in the LAN. The code so far configures automatic learning and
uses a default for aging of the learned addresses.

## L2 Tables
Access to the tables is done using table access registers. The same access
registers also provide access to the VLAN configuration tables. An idea of how
the table works can be gained from the [RTL8369 Datasheet](http://realtek.info/pdf/rtl8366_8369_datasheet_1-1.pdf)
section 8.17 and in particular table 20.

The central table register is RTL837X_TBL_CTRL(0x5cac).
```
Register RTL837X_TBL_CTRL bytes: EE EE TT CC
EE: Entry
TT: Table type
CC: Command (Bit 0: Execute, Bit 1: Write)
TT: 04: TBL_L2_UNICAST, 03: TBL_VLAN
```

An entry is retrieved from the tables by setting the data in registers to the
desired entry filter, then executing a table command by writing to RTL837X_TBL_CTRL
with execute bit 0 set, table type set and entry identifier (VLAN-Id or hash for L2).
Data will be fetched from the table and is available once the execute bit has been
cleared by the ASIC. Data then is in the output data registers

```
#define RTL837x_L2_DATA_OUT_A	0x5ccc
#define RTL837x_L2_DATA_OUT_B	0x5cd0
#define RTL837x_L2_DATA_OUT_C	0x5cd4

DATA_OUT_A   DATA_OUT_B   L2_DATA_OUT_C
M2 M3 M4 M5  fV VV M0 M1  xx xF xx gg

M0-M5: 6 bytes of MAC, M0 is MSB
V: 12 bits of VLAN-ID
f: bit 5 set: Entry is valid, otherwise stale
   bit 6: bit 0 of port-number
   bit 7: bit 1 of port-number
g: bit 0: bit 2 of port-number
   bit 1: bit 3 of port-number (MSB)
   bit 2: bit 0 of entry-age
   bit 3: bit 1 of entry-age
   bit 4: bit 2 of entry-age (MSB)
F: bit 0: entry is static(1) or learned (0)
```
The next entry can be now found in RTL837x_TBL_DATA_0 (entry = RTL837x_TBL_DATA_0_bits(0-11) + 1),
which can be used to get the next entry by writing this value to RTL837X_TBL_CTRL
and executing again for the given table type. This entry number is probably a hash, for which
the algorithm is unknown.

Deleting the entire L2 table is done by checking and setting 0x53dc to 0x0, then writing
0x00010000 to register RTL837x_L2_TBL_CTRL and waiting until the bit 16 that was
set has cleared.

The word layout above is the RTL8372/RTL8373's. The RTL8370 (RTL836x) uses the
same table-access machinery but a different entry shape, measured on hardware;
see the next section.

## RTL836x (RTL8370) entry layout

The RTL836x answers a read-by-key or a next-bucket step through the TA registers:
staging goes through WRDATA 0x0510-0x0516, and the seven 16-bit result words are
read from RDDATA 0x0520 up. Every TA command answers with its status in
`RTL836x_TA_LUT_REG` (0x0502) once the engine has settled.
The field map that hardware experiments confirmed:

```
W0: MAC bytes 4-5 (MAC[4] in the high byte, MAC[5] in the low byte)
W1: MAC bytes 2-3
W2: MAC bytes 0-1
W3: bit 15: static entry(1) — set by the fabric itself on entries it pins;
    bits 11:0: FID — learned entries read back as FID 1 on a switch whose
    VLANs are all untagged under FID 1
W4: bits 15:11: age, a countdown that starts at 6 when the fabric learns or
    refreshes an entry and decreases while the entry is unused;
    bits 10:8:  spa, the fabric port the MAC was learned on — confirmed by
    flushing single ports (only the entries whose spa names the flushed port
    disappear) and by the per-port learned-count registers 0x0a87+p agreeing
    with the spa decode
W5: bit 6: LIVE, set on every entry the fabric itself wrote; a staged write
    from the CPU also comes back with it set once accepted
W6: no data in any view (reads back 0 on this die); multicast entries replace
    the age|spa byte with their member mask (see the static-multicast note
    below)
```

The static bit and the age/spa byte live in W3/W4 where the 8372/3 keep port
bits in DATA_OUT_C — the reason the RTL836x walk used to report ports as
unknown.

### Write handshake (`0x0502` after the WRITE)

Every engine command ends with a status word in `RTL836x_TA_LUT_REG` (0x0502).
After a WRITE that stored an entry, the status carries the found bit
(`RTL836x_TA_LUT_FOUND`, 0x1000) plus the staged key's hash base in the low
bits: measured live, a fresh group entry answered 0x51a0 and the entry was
then in the walk at slot 0x09a0 — the 4-way bucket keeps the base in its low
11 bits and selects the way in bit 11. A write that replaces an existing
entry answers with the same base but different flags (0x1288 where the fresh
write answered 0x5188 for the same slot); the found bit is set in both
shapes. So the die's honest store-verification is to read that status word
right after the WRITE command — `port_l2mc_set()` and
`port_l2_static_mgmt()` do exactly that and print it (`mc L2 entry written,
look-up status ...`).

A by-key lookup restage — what the RTL8372/3 does to verify a write — works
on this die for unicast keys (a staged held entry was found with
status FOUND | slot), but the fabric answers *no such entry* to every
read-by-key of a multicast key: all 16 key-type bit pattern were staged
against the group MAC and all missed, while read-by-address on the same slot
proved the entry stored. Group entries are therefore verified only through
the write handshake above.

`rtl836x_l2_unpack()` fills `l2_walk.port` from W4 bits 10:8 and
`l2_walk.is_static` from W3 bit 15, and `held()` keeps an entry by checking the
static bit instead of a load count.

A static entry survives an L2 flush while dynamic entries vanish. Its age
field is not frozen, though: it counts down like a learned entry's, and the
fabric raises it back to 6 when traffic addressed to that MAC arrives or the
CPU transmits. An idle static entry therefore ages out eventually — which is
why `port_l2_static_mgmt()` re-pins the CPU's entry at boot.

`port_l2_static_mgmt()` stages the device's own MAC as a static entry so the
fabric never floods it and the LUT always names the CPU's LUT port for it:
W0-W2 carry the MAC, W3 = 0x8001 (static bit set, FID 1), W4 =
(6 << 11) | (spa << 8) naming the CPU NIC's fabric port (patched at boot;
spa 2 on the Sodola), W5 = LIVE only. The fabric normalizes a staged W4 of 0
or an age above 6 down to age 6 and stores the spa verbatim. The `l2` command
prints the entry as `static CPU`, and the web MAC table flags it
(`"iscpu":"1"` in l2.json) instead of showing whichever spa it carries.

## API support in the code
The RTLPlayground code provides support for reading the L2 tables from the
ASIC and flushing the table in order to quickly forget the learned entries.
```
> l2
        MAC       VLAN    type    port
3c:18:a0:7e:11:00 0x0001  learned 5
1c:2a:a3:23:00:02 0x0001  learned 7
```

## Static multicast entries

Slow-protocol frames such as LACPDUs and STP BPDUs have to reach the CPU
without being flooded to the other ports. No bridge relays these frames:
their addresses are in the set that 802.1D-2004 clause 7.12.6 forbids a
bridge to forward, and what travels the network is the information, with
every bridge regenerating BPDUs of its own on its designated ports. The reserved-multicast *trap* action
does that: it delivers to the port named in `EXT_CPU_CTRL` (0x6724), which
`trap_init()` sets to 9, the CPU port, at startup; with the reset value 0xf it
names no port and the trapped frame is dropped. STP traps its address while it
runs (see stp.md). Where the action is left at *forward*, the egress can be
constrained with a static L2 multicast entry instead: the lookup hits the
entry's own port mask rather than the VLAN flood mask. Verified on a SWTGW218AS
both ways, with the CPU bit cleared, where delivery stops, and with the CPU bit
alone, where nothing egresses.

`port_l2mc_set()` writes one such entry. The SMI layout is the L2 multicast
variant of the table entry — for the RTL8372/3 through the three data-in
registers DataInA/B/C:

```
DATA_IN_A = MAC bytes 5..2                            -> c2 00 00 <mac_last>
DATA_IN_B = MAC[1..0] | vid<<16 | IVL<<29 | pmask[1:0]<<30
DATA_IN_C = pmask[9:2]
```

Lookups are IVL, so an entry made for VID 0 is never matched and a caller adds
one entry per PVID in use (the firmware builds one entry for each PVID in use
at each `stp_fdb_update()`, and hardware showed the fabric applies the staged
content to its own hash bucket: the entry was written at the computed bucket
for its key base). The write goes through the table access register
with the table selector set to the L2 lookup table, `TBL_L2_UNICAST` in the
code, a name that despite appearances covers the multicast entries as well.
The hardware hashes MAC and VID to pick the bucket slot by itself.
Writing the same MAC and VID again replaces the entry rather than adding a
second one, so a caller can retarget the mask at will, for instance back to all
ports to restore flooding. See the RTL836x layout sections above for this
die's word-shaped variant.

On the RTL836x the entry is staged as seven words through WRDATA 0x0510
and committed with the L2 WRITE code (0x0c):

```
W0 = mac_last (low byte)
W1 = 0xc200   W2 = 0x0180                the group address 01:80:c2:00:00:x
W3 = 0x8000 | (vid & 0x0ff)              static bit + the entry's FID/VID
W4 = member mask                         ports 0-7 in bits 7:0, CPU (bit 10)
W5 = W6 = 0                              no live flag: the entry holds on its
                                         static bit plus a non-zero mask
```

The member mask uses the die's port-frame numbering (front ports in bits 0-7,
bits 8-9 unused, CPU at bit 10); the die stores it verbatim — masks as wide as
0x4ff (flood) and as narrow as 0x400 (CPU only) both came back through the
walk unchanged. `stp_on()` writes the entries with CPU-only masks (via its
trap setup or through `stp_fdb_update(PMASK_CPU)`), `stp_off()` restores flood
spanning with `PMASK_CPU | PMASK_PORT` — the difference is what the `stp
bpdu filter|flood` toggle retargets.
